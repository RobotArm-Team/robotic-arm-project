# 协作规则

## 工作流

1. 从 GitHub Issue 开始：描述目标、负责人、验收数字、截止时间和关联需求编号。
2. 新建分支：`feature/<issue-number>-<short-name>`、`docs/<issue-number>-<short-name>` 或 `fix/<issue-number>-<short-name>`。
3. 在分支完成一个可审阅的改动后提交 Pull Request；PR 必须关联 Issue。
4. 至少一位非提交者审阅后，方可合并到 `main`。
5. 合并后关闭 Issue；版本节点打 tag，例如 `v0.1-requirements`、`v0.2-integration`、`v1.0-demo`。

`main` 应始终保持可阅读、可演示；不要直接推送到 `main`。

## 负责人

| 领域 | 第一负责人 | 审阅时应重点关注 |
|---|---|---|
| 手势、语音、数据质量、系统测试与验收 | A | 触发安全、测试证据、验收数字。 |
| 视觉、数据、YOLOv8、部署、总体集成与发布 | B | 数据版本、指标口径、接口边界、发布影响。 |
| 标定、ROS2、Arm_Lib、安全边界 | C | 工作区、角度限位、急停、回退路径。 |
| F3 全栈、事件服务、Web、异常日志 | D | 接口字段、状态一致性、日志可追溯性。 |

## PR 最低要求

- 使用仓库 PR 模板；
- 说明“改了什么、为何要改、如何验证、是否影响接口或安全”；
- 接口改动同时更新 `api/openapi.yaml`；
- 需求、验收指标或安全规则改动同时创建 OpenSpec 变更；
- 不上传原始人脸/手势图像、原始语音、密钥、个人路径或大型模型权重；
- 若改动涉及机械臂，写明是否在真机执行，且不得把未验证的真机结论写成已通过。

## 飞书与 GitHub 的分工

- **飞书：** 周会纪要、硬件预约、现场照片/视频链接、临时沟通。
- **GitHub：** 需求版本、Issue、代码、PR、接口契约、评审记录和可提交的证据。

飞书中的决定必须由负责人同步到对应 Issue 或文档；否则不视为正式基线变更。

## 变更管理

需求、接口、安全门禁或范围边界的变化先走 [OpenSpec 流程](../openspec/README.md)。紧急停机和安全修复可先处理，但必须在恢复后补充事件记录与 PR 说明。
