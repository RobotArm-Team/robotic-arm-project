# OpenSpec 变更流程

本目录只管理会影响需求基线的变更：范围、验收数字、接口字段、硬件约束、风险处置或安全门禁。普通实现细节不必走 OpenSpec。

## 何时必须创建变更

- 改变 F1–F4 或 E1–E2 的验收数字；
- 新增、删除或改写“明确不做”的范围边界；
- 修改 `api/openapi.yaml` 的已有字段语义、单位或错误码；
- 放宽或收紧工作区、舵机限位、急停、重试次数等安全规则；
- 因硬件能力与原需求不符而需要降级。

## 目录与命名

```text
openspec/
└── changes/
    └── YYYY-MM-DD-<short-name>/
        ├── proposal.md      # 为什么要改、影响谁
        ├── specification.md # 修改后的明确行为和验收条件
        └── tasks.md         # 必须同步修改的代码、接口、文档和证据
```

## 审核流程

1. 提出者创建对应 GitHub Issue，并说明当前基线、拟议变化和风险。
2. 在 `openspec/changes/` 新建变更记录，并由受影响模块负责人审阅。
3. 审阅通过后，实施代码、接口、文档改动；同一 PR 必须链接该 Issue 与变更目录。
4. 合并后，将已生效的规则同步回 `docs/requirements/requirements-baseline.md` 与相关架构文档。

> 发生急停或安全故障时，以停机和安全处理为先；但恢复后必须补齐变更/事件记录。
